# ADR-016: Hybrid Quality Validation Boundary

## Status

Accepted — 2026-09-16

## Context

The project has reached L-U6 (Camera/Motion/Sound Compiler). The pipeline
produces a comprehensive semantic production plan: a `PromptCompilationResult`
(L-U5), a `CameraMotionSoundCompilationResult` (L-U6), a
`CharacterReferenceSpecification` (L-U4), and a `StoryboardPackage` (P5).

Before the system proceeds to provider integration, generation, or
rendering, the project needs a **quality gate** that checks the correctness
of the semantic production plan *without itself becoming a generator*.

## Decision

Implement **L-U7 — Hybrid Quality Validation Engine** as a **read-only,
deterministic, provider-neutral, renderer-neutral** validation layer.

L-U7 consumes existing canonical contracts and produces a
`QualityValidationResult` with status PASS / WARN / REJECT / UNAVAILABLE.

## Rationale

### 1. Why validation lives after L-U6

L-U7 is positioned after L-U6 because:

- L-U5 produces `CanonicalPromptIR` (canonical prompt structure).
- L-U6 enriches that IR with camera/motion/sound semantics.
- L-U4 already establishes identity vs scene state.
- L-U3 establishes knowledge provenance.

The semantic production plan is **complete** at this point. L-U7 verifies
that completeness, consistency, traceability, and qualification before
downstream stages.

### 2. Why validator does not mutate upstream contracts

Mutation would create hidden coupling between validation and generation.
The validator must:

- Report issues, never fix them.
- Allow the same validation to be re-run on the same inputs.
- Provide reproducible fingerprints.
- Allow consumers to inspect both the issue AND the original contract.

Validation ≠ normalization.

### 3. Why no LLM in L-U7

LLMs introduce:

- Non-determinism (random seed, model version).
- Hidden assumptions about "expected" values.
- Cost and latency in the critical path.
- Difficulty in reproducibility.

L-U7 instead uses **deterministic structural checks** + **domain-specific
semantic rules** + **cross-contract validation** + **provenance validation**.

This is called "Hybrid Validation" — but hybrid does NOT mean AI.

### 4. Why hybrid = structural + semantic + cross-contract + provenance

- **Structural**: Pydantic field presence, type checks.
- **Semantic**: domain rules (camera direction, motion vocabulary).
- **Cross-Contract**: PCR ↔ CMS ↔ CharacterReference ↔ Storyboard.
- **Provenance**: knowledge-derived fields have traceability.

Together, these cover the main failure modes without LLMs.

### 5. Why provider/renderer are forbidden

The Provider Adapter Layer is the **next** architectural boundary. It
must consume a fully validated semantic plan. If L-U7 itself depended on
provider SDKs, validation would require running provider APIs — which is
both expensive and incorrect.

Similarly, rendering (Remotion/FFmpeg) belongs to the Editorial layer.
L-U7 cannot touch timing/audio mixing without colliding with that authority.

### 6. Why quality decision is not a numeric ranking

A numeric score (e.g., 93/100) implies ranking and comparison across
scenes. Quality decisions in L-U7 are **categorical**:

- PASS: proceed
- WARN: proceed with notes
- REJECT: do not proceed
- UNAVAILABLE: cannot determine

These are decision-states, not scores. There is no "B-grade scene".

### 7. Why Character identity authority remains L-U4

L-U4 established:

- `CharacterReferenceSpecification` is the identity authority.
- Identity ≠ Scene State is the core invariant.

L-U7 enforces this invariant. It does NOT replace L-U4. The Character
System Engine (PROMPT 5) consumes L-U4 specifications and may choose to
ignore them with explicit override — L-U7 surfaces such overrides via
the conflict dimension but does not block them.

### 8. Why timing authority does not change

P7 (Animation), P8 (Voice), and P9 (Editorial) own frame-level timing.
L-U7 has no concept of frames, fps, or wall-clock duration. It validates
**semantic** duration (e.g., "VIDEO must have movement") not technical
duration (e.g., "must be ≤ 30 seconds").

## Consequences

### Positive

- Clean separation of concerns: validation is decoupled from generation.
- Validation is fast, deterministic, and reproducible.
- Issues are traceable to concrete contract fields.
- Provider/Renderer layers can be tested independently.
- Tests can construct arbitrary upstream contracts and run validation.

### Negative

- L-U7 cannot detect semantic issues that require deep understanding
  (e.g., "this scene description is too vague"). This is left to the
  Provider Adapter Layer (FUTURE) and to human review.

### Neutral

- L-U7 introduces 15 new validation dimensions.
- L-U7 introduces a new status vocabulary (PASS/WARN/REJECT/UNAVAILABLE).
- L-U7 introduces a new policy model (STRICT/STANDARD/LENIENT).

## Alternatives Considered

### Alternative A: Validation built into L-U6 compiler

Rejected. Conflating compilation and validation breaks single responsibility
and makes it harder to validate multiple compilation outputs together
(e.g., cross-scene continuity).

### Alternative B: Validation built into L-U5 compiler

Rejected. L-U5 stops at `CanonicalPromptIR`. L-U7 needs camera/motion/sound
semantics from L-U6 to validate those dimensions.

### Alternative C: Validation built into Provider Adapter Layer

Rejected. Provider Adapter Layer is FORBIDDEN from importing provider
SDKs in L-U7 territory. Validation must happen BEFORE provider integration.

### Alternative D: LLM-based validation

Rejected. Non-deterministic, expensive, and unverifiable. See §3.
