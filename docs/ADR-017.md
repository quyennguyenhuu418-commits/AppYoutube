# ADR-017: Provider Adapter Layer

**Status:** Accepted

**Date:** 2026-09-16

**Author:** L-U8 Implementation

---

## Context

The AI Documentary Animation / Video Factory has built a canonical semantic
production pipeline (L-U1 through L-U8) that produces structured, provider-neutral
semantic contracts:

- `CanonicalPromptIR` (L-U5)
- `CameraMotionSoundCompilationResult` (L-U6)
- `CharacterReferenceSpecification` (L-U4)
- `QualityValidationResult` (L-U7)

These contracts represent semantic production intent without specifying how a
particular provider encodes it. Before actual generation can occur, this
semantic intent must be translated into provider-specific representations.

The question is: **how should the system translate canonical semantic contracts
to provider-specific generation requests?**

---

## Decision

Implement a canonical Provider Adapter Layer (L-U8) with:

1. **Provider Abstraction** — `ProviderDefinition` (canonical metadata) and
   `ProviderType` (semantic categories, not business logic).
2. **Capability Registry** — `ProviderRegistry` as single source of truth,
   `ProviderCapability` (task-specific capability), `CapabilityMatcher`
   (deterministic compatibility matching, no ranking).
3. **Provider Prompt Adapter** — `ProviderPromptAdapter` abstract interface,
   `ProviderPromptRepresentation` output, `MockGenerationProviderAdapter`
   for testing.
4. **Semantic Loss Report** — mandatory field-level translation status
   (SUPPORTED / TRANSFORMED / APPROXIMATED / OMITTED_WITH_REASON / UNSUPPORTED).
5. **Provider Generation Request** — canonical execution boundary contract.
6. **Error Taxonomy** — canonical error kinds with retry classification.
7. **Quality Gate Integration** — L-U7 as the authority for compilation gating.

---

## Rationale

### Why not extend the existing `app/providers/` module?

The existing `app/providers/` module (Prompt 3.5) handles LLM, TTS, Search, and
Content Fetch — runtime execution providers. These are operational providers
with real API calls.

L-U8 is a **translation layer** for Image/Video generation. It is conceptually
separate: it translates semantic contracts to provider representations,
but does not execute generation. Keeping these separate:

- Avoids mixing operational concerns (API calls, retries) with semantic concerns
- Allows L-U8 to exist before any real provider integration is verified
- Makes the boundary between "semantic" and "provider-specific" explicit

### Why not just use raw strings?

Raw strings lack:
- Semantic structure that can be validated, matched, and compared
- Traceability from generation request back to semantic intent
- Deterministic fingerprinting based on semantic content

Structured representations allow:
- Capability matching against semantic requirements
- Semantic loss reporting (which fields survived translation)
- Deterministic fingerprints independent of formatting changes

### Why not make L-U8 do real generation?

Separation of concerns:
- **Translation** (L-U8): semantic -> provider representation
- **Execution** (future): provider representation -> media

Mixing these would:
- Make L-U8 too large and coupled to provider SDKs
- Prevent testing without real API keys and network access
- Violate the "canonical contracts are authority" principle

### Why deterministic capability matching only?

Ranking providers (e.g., "best provider for this task") requires:
- Runtime performance data
- Cost analysis
- User preference modeling
- Quality metrics at scale

These are operational decisions outside the scope of L-U8. L-U8 only
determines **compatibility** — whether a provider can satisfy a requirement.

---

## Consequences

### Positive

- Clear boundary between semantic layer and provider layer
- Deterministic, testable translation without real providers
- Mandatory semantic loss reporting prevents silent degradation
- Quality gate integration ensures L-U7 authority is respected
- Error taxonomy enables future retry engine implementation

### Negative

- Additional abstraction layer with new contracts to maintain
- Capability matching is conservative (UNKNOWN = not supported by default)
- Mock providers may diverge from real provider behavior when integrated

### Neutral

- No real provider execution verified yet (structural-only)
- Provider SDKs not yet imported into the generation layer
- Generation runtime infrastructure (queues, schedulers) not implemented

## Implementation

### Files Created

| File | Description |
|---|---|
| `app/providers/generation/schemas.py` | Canonical Pydantic contracts |
| `app/providers/generation/registry.py` | ProviderRegistry + defaults |
| `app/providers/generation/matcher.py` | Deterministic CapabilityMatcher |
| `app/providers/generation/mock_adapter.py` | MockGenerationProviderAdapter |
| `app/providers/generation/__init__.py` | Public API exports |
| `tests/test_provider_adapter_layer.py` | 94 comprehensive tests |

### Key Design Decisions

1. **ProviderType is semantic, not provider-specific** — categories like
   IMAGE_GENERATION rather than "DALL-E" or "Stable Diffusion"

2. **Semantic loss is mandatory, not optional** — every field must appear
   in the report with an explicit status; silent dropping is prohibited

3. **QualityValidationResult.REJECT blocks compilation** — the adapter
   itself does not enforce this; the caller must check and enforce

4. **Fingerprints are semantic, not random** — SHA-256[:32] of semantic
   content only; no timestamps, random UUIDs, or secrets

5. **Verification status is explicit** — VERIFIED (runtime-tested),
   DECLARED (documented), UNKNOWN (no evidence); DECLARED != VERIFIED
